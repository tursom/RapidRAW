# Windows：阶段 1 第 5 项剪贴板占用与直接读取

**Windows 本项补测已完成，阶段 1 整体仍不通过。** 本轮只增加独立实验、证据和报告修正；正式六态粘贴、输入入口和调整参数应用均未实现。macOS、资源管理器、真实 RAW、纯多图、系统截图、复制图片地址、真实网站及 PNG/WebP 拖放仍待人工补测。

## 结论与参数建议

1. **占用已直接复现。** 首次序列变化后立即读取两张 6000×4000 图，在 0/50/150/350ms 四档共 48 次均失败；失败后立即单次 `OpenClipboard` 的明确错误码均为 **5（拒绝访问）**。700/1500/3000ms 三档共 36 次均读到完整 PNG。旧报告没有识别打开失败被库吞掉的机制，也没有指出前置探测掩盖了等待，现予修正。
2. **3 秒可保留为本机的打开等待预算候选。** 12 次显式轮询均在首次序列变化后约 **553–614ms** 首次打开成功；全部浏览器样本中最后一次序列变化距菜单释放最晚约 **889ms**。本轮没有遇到浏览器持续占用超过 3 秒，但这不是所有机器、网站或 macOS 的上界。辅助进程持锁 3.5 秒时，3 秒预算后仍明确打开失败，应提示忙，不能转为无内容。
3. **200ms 不是完成判据。** 12 个不读取内容、不打开剪贴板的纯观察样本，都出现过“序列号静默 200ms、浏览器仍持有剪贴板、随后继续变化”；Edge 高熵图中两次连 500ms 静默也不是完成信号。200ms 可以作为重读的观察间隔候选，但必须结合显式打开、序列复核和再次读取；本实验没有实现完整六态流程，不能宣称该流程已通过。
4. **另有尚未发布的复制窗口。** 从菜单释放立即读时，18/18 次仍读不到 PNG，却能读到本实验预置的旧 `RapidRAW:adjustments` 标记；稍后均读到了本次图片。这是系统状态的实测，不是已复现应用错误套用。当前计划中“读到 marker 立即返回”仍须考虑这个边界：外部复制尚未更新系统剪贴板时，打开可能成功、序列号可能不变。锁重试本身无法识别未来的外部复制意图，不能把这个阶段当作已确认可以应用旧参数。需在任务 10 前明确该边界并验收，本轮不擅改产品策略。

`busy`、`failed` 不回退参数的计划保持必要；**不把 `get_buffer` 错误文本解析成 busy/none，也不把枚举为空当作无内容。**

## 环境、来源和计时

2026-11-06 至 2026-11-07，`pc.lan` Windows 10 x64 10.0.19045，已登录桌面 Session 1，AMD Ryzen 7 5800X3D。Rust/Cargo 1.99.1，`clipboard-rs = 0.3.5`，直接依赖既有同版本 `clipboard-win = 5.4.3`。Chrome 157.0.8103.38、Edge 156.0.4314.58。环境及清理核验见 [environment-cleanup.json](environment-cleanup.json)。

复用上轮的三张素材：`small.jpg` 1024×768；`large.jpg` 6000×4000 高熵生成图；`photo-control.jpg` 6000×4000 放大照片对照。后者来自仓库 2048×2048 照片，不是原生 24MP 相机照片。输入大小与 SHA-256 保存在原始 JSON，页面为本机 `http://127.0.0.1:8769/clipboard-contention.html`，不算真实网站覆盖。

每次复制前用 Win32 生成已知旧标记，模拟之前已复制调整参数的剪贴板状态；然后使用浏览器真实“复制图片/图像”菜单。早期样本以物理鼠标打开菜单，后续为避免 Edge 欢迎页/窗口干扰，使用绑定到素材标签的 CDP 可信 `contextmenu` 输入打开原生菜单；**触发复制的菜单选择始终使用真实 Win32 鼠标释放**。没有用 JS 写入 PNG 或模拟系统复制结果。

Rust release 读取器在点击菜单之前就启动并创建上下文。它先输出 `ready`，并以不打开剪贴板的观察线程记录序列号、当前打开窗口和所属 PID。每次必须重新复制，不把同一份内容的重复读取充当不同延迟样本。

- `direct` 的首个内容操作是 `get_buffer("PNG")`。之前没有格式枚举、文件、文本、`has()` 或显式打开；序列号和窗口查询不取内容、不加锁。
- `open-retry` 是独立对照：用 `clipboard_win::Clipboard::new()` 单次尝试，失败后每 50ms 再试，最多约 3 秒；保存真实 `Err(e).raw_code()`。不读取图片。
- `observe` 是独立纯观察对照，不打开或读取剪贴板。
- 直读失败后的显式打开、可选文本诊断都在 PNG 读取结束之后，不能算成读取之前的等待。库返回后的线程 last-error 仅作诊断，不作为失败阶段或内容类型判据。
- 观察持续到计时起点后约 3.4 秒；**完整 PNG 解码和摘要在观察结束之后执行**，再独立读取稳定 PNG 三次，核对来源、完整字节和像素。

QPC 计数器连接 Python 的菜单释放、Rust 的读取起止与观察事件。查询请求间隔为 1ms，实际受 Windows 调度影响；各 Win32 查询也不是原子快照。报告因此给出观测范围和打开失败/成功边界，不声称精确到 1ms 的连续锁时长。

## 首次序列变化起点：114 个浏览器样本

[sequence.json](sequence.json) 包含 90 次直读、12 次显式打开轮询、12 次纯观察，另有 10 个生成控制用例。每个浏览器、每张大图、每档各 3 次，小图各 3 次。该起点代表观察到剪贴板开始变化，**不代表复制已完成**；菜单释放时间也完整保留。

| 来源 / 素材            | 0ms | 50ms | 150ms | 350ms | 700ms | 1500ms | 3000ms |
| ---------------------- | --: | ---: | ----: | ----: | ----: | -----: | -----: |
| Chrome / 高熵大 JPEG   | 0/3 |  0/3 |   0/3 |   0/3 |   3/3 |    3/3 |    3/3 |
| Chrome / 放大照片 JPEG | 0/3 |  0/3 |   0/3 |   0/3 |   3/3 |    3/3 |    3/3 |
| Edge / 高熵大 JPEG     | 0/3 |  0/3 |   0/3 |   0/3 |   3/3 |    3/3 |    3/3 |
| Edge / 放大照片 JPEG   | 0/3 |  0/3 |   0/3 |   0/3 |   3/3 |    3/3 |    3/3 |

单元格为 PNG 成功次数/尝试数。小图在首次序列变化后立即读取，两浏览器各 3/3 成功。共 **42 次成功、48 次失败**；成功结果全能完整解码，尺寸、RGBA8 摘要及原始字节均与来源和后续参考读取一致，没有观察到“成功返回不完整 PNG”。失败调用本身持续约 **144–196ms**，且随后显式单次打开均捕获错误码 5。

`new_attempts(10)` 源码是首次加 10 次重试、10 次 `Sleep(5)`，名义睡眠总和 50ms；Windows 调度下本轮实际约 150ms，不能把名义值当作精确耗时。这也与上轮大图格式枚举约 155ms、其他尺寸约 0.05ms 的规律吻合。

显式打开轮询的边界如下，单位 ms，起点仍为首次序列变化：

| 来源 / 素材            | 三次末次打开失败的范围 | 三次首次打开成功的范围 |
| ---------------------- | ---------------------: | ---------------------: |
| Chrome / 高熵大 JPEG   |          502.94–504.76 |          553.21–554.91 |
| Chrome / 放大照片 JPEG |          503.27–519.48 |          553.87–569.74 |
| Edge / 高熵大 JPEG     |          554.81–563.28 |          605.37–613.90 |
| Edge / 放大照片 JPEG   |          503.50–505.96 |          554.07–556.57 |

这是 50ms 轮询下的边界，不是锁释放瞬间。本实验的循环在休眠后再尝试，3.5 秒持锁控制的末次尝试实际在约 3023ms；它不是已经实现严格截止时间的正式流程。若正式代码改用 `new_attempts(10)`，内部已有一轮等待，再睡 50ms 后的周期也不能直接按本表理解。`GetClipboardData`、PNG 验证和导入写盘是另外的耗时；一个外层 3 秒打开预算也不能强行中止已经开始的同步 `GetClipboardData`。

纯观察样本中，最后一次序列变化距菜单释放的范围为：Chrome 高熵图 634.53–647.06ms、照片 624.32–629.48ms；Edge 高熵图 664.53–711.06ms、照片 638.93–682.37ms。纯观察也持续写入，排除了“所有变化都是读取器触发”的解释。完整矩阵中首次发布最晚约 300.58ms，最后变化最晚约 888.85ms。

## 菜单释放起点：54 个补充样本

[dispatch.json](dispatch.json) 使用预先待命的 Rust 进程：Python 发出真实鼠标释放后，立即经 stdin 发 `go`；Rust 收到后才开始该档等待。`go` 起点比鼠标释放晚 **0.013–0.033ms**，不是等待首次序列变化。两张大图测 0/200/350/700ms，每格各 3 次；小图测 0ms，各 3 次。

| 来源 / 素材            |               0ms |           200ms |           350ms | 700ms |
| ---------------------- | ----------------: | --------------: | --------------: | ----: |
| Chrome / 高熵大 JPEG   | 0/3，旧标记仍可读 | 0/3，打开错误 5 | 0/3，打开错误 5 |   3/3 |
| Chrome / 放大照片 JPEG | 0/3，旧标记仍可读 | 0/3，打开错误 5 | 0/3，打开错误 5 |   3/3 |
| Edge / 高熵大 JPEG     | 0/3，旧标记仍可读 | 0/3，打开错误 5 | 0/3，打开错误 5 |   3/3 |
| Edge / 放大照片 JPEG   | 0/3，旧标记仍可读 | 0/3，打开错误 5 | 0/3，打开错误 5 |   3/3 |

小图 0ms 也均为 0/3，失败后读到旧标记。共 **12 次完整 PNG 成功、42 次失败**；0ms 档合计 **18 次 PNG 不存在于当次读取中，而旧标记仍成功可读**。200/350ms 的 24 次失败随后单次打开均返回错误码 5。这里的 0ms 是极早的调用，不能直接当作普通用户延迟分布或实际错误套用次数；但它证明了“尚未发布”和“已经占用”是两个不同阶段。

该组首次序列变化最晚约 274.29ms，最后变化最晚约 828.54ms。文本诊断只在 PNG 失败后执行，并单独记录时间和序列号；不会掩盖首个 PNG 读取的失败。所有成功 PNG 都与后续完整参考字节相同。

## 10 个控制用例

辅助进程创建真实隐藏 HWND，显式打开并持锁；有打开/释放 QPC，已核对读取确实在持锁期内开始。最初使用 NULL HWND 的辅助进程未完成预期的持锁/释放生命周期，属于无效控制，已保留在 `discardedControls` 和失败归档，不作为结论依据。

| 控制                                       | 结果                                                                                             |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------ |
| 持锁 100ms / 350ms / 1000ms，50ms 显式轮询 | 首次打开成功约 101.51 / 352.36 / 1008.19ms                                                       |
| 持锁 3500ms，3 秒显式轮询                  | 61 次明确打开失败，末次约 3022.95ms；3.4 秒末次检查仍失败，不能当 none                           |
| 持锁期间原库 PNG 直读                      | 失败；100ms 档读到的错误文本仍含代码 5，但随后显式打开已成功，说明不能单凭库错误文本判断当前状态 |
| 稳定旧标记、空剪贴板                       | PNG 读取失败，库文本为 `OSError(0)`；显式打开成功，与长时占用的明确打开失败不同                  |

控制数据只证明相关 Win32 行为和诊断边界，没有实现正式应用的 `busy/failed/none/marker` 返回或参数应用。

## 证据、复算与复现

- [summary-sequence.json](summary-sequence.json)、[summary-dispatch.json](summary-dispatch.json)：按浏览器、素材、模式、间隔分组的统计，含输入 SHA-256；[汇总脚本](../../../scripts/summarize-clipboard-contention.py) 无 Windows 依赖，可独立复算。
- [inputs/manifest.json](inputs/manifest.json)：原始源码输入的 SHA-256 与精确快照路径。首次序列组使用历史 Rust 输入 [probe-sequence.rs](inputs/probe-sequence.rs)；菜单释放组使用当前仓库探针。驱动修复前后的输入均保留，避免仅凭“只改了格式”等声明判断差异。
- [build-records/](build-records/)：两次 release 构建、Windows Clippy 和运行退出码均为 0。日志统一为 UTF-8/LF，未改错误内容。
- [prior-attempts.zip](prior-attempts.zip)：完整保留连接中断、Edge 标签/窗口绑定、无效持锁器等失败尝试。失败发生在准备复制或无效控制阶段，不计入有效浏览器测量；已有有效行按唯一用例 ID 续跑，完成时检查完整集合。不能把未验证尾行或部分矩阵改成完成。

复算：

```sh
python spike/intake/scripts/summarize-clipboard-contention.py spike/intake/evidence/windows/contention/sequence.json
python spike/intake/scripts/summarize-clipboard-contention.py spike/intake/evidence/windows/contention/dispatch.json
```

Windows 在已登录图形桌面、独立应用 `src-tauri/` 内构建：

```powershell
cargo build --locked --offline --release --no-default-features --example clipboard_contention
```

将构建出的 `target/release/examples/clipboard_contention.exe` 分别复制为项目根 `artifacts/clipboard-contention.exe` 和 `artifacts/clipboard-contention-dispatch.exe`，在项目根用既有 venv 运行：

```powershell
.\venv\Scripts\python.exe -X utf8 -u .\spike\intake\scripts\windows-clipboard-contention.py
.\venv\Scripts\python.exe -X utf8 -u .\spike\intake\scripts\windows-clipboard-contention.py --dispatch
```

当前源码支持两种起点；若要核对历史首次序列组的精确构建输入，使用归档 Rust 快照。需要保留原有素材与旧 release CLI（独立参考驱动导入时核对该文件）。`--resume` 验证程序和素材摘要，保留未验证记录并明确重跑；拒绝续跑写到独立文件，不能覆盖原始结果。辅助控制按完整唯一集合校验。源码及驱动不含登录凭据。

Windows 已保留两份实际测量产物，原有 debug/release 窗口也保留。清理核验本轮 3 个计划任务和专用进程剩余均为 0。**本项 Windows 完成不替代 macOS、真实截图或其他人工验收，也不解除任务 10 的前提。**
